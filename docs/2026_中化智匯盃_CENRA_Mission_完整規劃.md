## 一、執行摘要

現有原型已完成成交預測、風險異常、拜訪排序、地圖、產品建議、通知與 Human-in-the-Loop 等多項功能，但各功能平行陳列，缺乏單一且鮮明的使用者痛點。新版不再以「多功能 Dashboard」為產品，而是聚焦一個真實的工作時刻：

> 診所通路業務每天出門前，必須在新客開發、舊客挽回與既有客戶成長之間分配有限外勤時間，但現有 CRM 主要保存過去紀錄，無法直接回答「今天最值得做哪一件事」。

新版產品定義為 **AI 診所業務任務指揮台**。目標架構每天從 CRM、訂單、產品、帳款與地理資料中產生三類候選任務；四天原型先使用最小資料樣例展示流程，最後仍由業務決定如何執行：

1. **攻｜開發任務**：找出值得接觸的高潛力新診所。
2. **守｜挽回任務**：找出尚未完全流失、現在介入仍可能挽回的既有診所。
3. **增｜成長任務**：找出補貨、品項擴張或客戶價值提升機會。

三類任務不是三套獨立產品，而是共同進入同一個「任務價值排序引擎」，最後形成每位業務員今日最值得執行的任務清單。每張任務卡必須同時回答：

- 為什麼是現在？
- 如果不處理，可能錯失什麼？
- 這一趟的明確目的為何？
- 出門前要準備哪些資訊？
- 證據有多強？還需要業務確認什麼？

### 2.1 中化裕民確實存在外勤拜訪場景

公開資料支持以下事實：

- 中化裕民是中化旗下的商業化與市場拓展平台，產品涵蓋處方藥、OTC、營養補充品、個人護理與醫療器材，通路橫跨醫院、診所、藥局與零售通路。

### 2.2 本提案不做的錯誤假設

公開資料沒有證明下列事項，因此簡報與 Demo 不可宣稱：

- 每位業務每天固定拜訪幾家診所。
- 中化裕民目前 CRM 一定具有特定欄位或 GPS 資料。

每日可用時間與固定預約在 Demo 中應標示為「可調整的情境參數」，不能描述成中化裕民現況。

## 三、產品定位

### 3.1 目標使用者

**第一使用者：診所通路外勤業務**

- 負責特定區域與診所客戶。
- 同時處理新客開發、舊客維繫、產品推廣及售後事項。
- 每天需要決定拜訪對象、拜訪目的與移動順序。
- 掌握大量非結構化客情，但不一定有時間完整閱讀 CRM 紀錄。

**第二使用者：區域業務主管**

- 關注高價值客戶是否被遺漏。
- 希望了解團隊如何分配外勤資源。
- 需要檢視 AI 任務被採納、修改或拒絕的原因。
- 關注任務完成後的營運結果，而不是單純看模型 AUC。

### 3.2 核心痛點

產品不把痛點描述成「沒有 Dashboard」，而是：

> 一位診所業務每天同時面對開發、挽回與成長機會；當所有客戶都看起來值得拜訪時，真正困難的是取捨。CRM 保存了許多紀錄，卻沒有將紀錄轉成有目的、可執行、可追蹤的今日任務。

### 3.3 核心價值主張

> CENRA Mission 將散落於 CRM、ERP 與客戶互動中的訊號，轉成業務今天可執行的任務，協助其在正確時間、帶著正確目的，拜訪正確的診所。

### 3.4 競賽記憶點

主標語：

> **CRM 記得昨天，CENRA Mission 讓業務決定今天。**

口頭開場：

> 業務每天不是沒有事情做，而是值得做的事情太多。真正昂貴的問題不是「哪位客戶可能下單」，而是「今天有限的外勤時間，應該先用在哪一個任務上」。

## 四、三類任務設計

### 4.1 攻｜高潛力新診所開發

**要回答的問題**

> 在尚未合作的診所中，哪些最值得業務投入首次接觸？

**可能資料訊號**

- 診所科別、規模與服務項目。
- 所在區域與既有服務範圍。
- 與中化產品線的適配度。
- 鄰近同類型既有客戶的產品採用情形。
- 距離既有拜訪路線的額外移動成本。
- 是否已有接觸紀錄、活動回應或公開合作訊號。

**任務卡輸出**

- 開發潛力分級，不虛構精確成交機率。
- 推薦接觸理由。
- 建議首次溝通的產品資訊類別。
- 鄰近可順訪的既有任務。
- 尚缺資料與需要人工確認的事項。

### 4.2 守｜既有診所流失挽回

**要回答的問題**

> 哪些既有診所尚未完全流失，但現在不介入可能錯過挽回窗口？

**可能資料訊號**

- 訂單金額、頻率或品項廣度連續下降。
- 原本穩定採購的核心品項停止購買。
- 距離上次有效互動時間過長。
- 拜訪後沒有形成下一步或承諾事項逾期。
- 業務紀錄出現競品、價格、缺貨或不滿等明確文字訊號。
- 帳款、退貨、客訴或售後問題未完成。

**任務卡輸出**

- 標示為「流失風險待查」，不可僅因異常分數就宣稱競品入侵。
- 顯示造成任務的可驗證證據。
- 顯示可能受影響的歷史營收或品項，不把它稱為已避免的損失。
- 建議確認問題、跟進承諾或提供適當資訊。
- 若證據不足，要求業務先電話確認，再決定是否實地拜訪。

### 4.3 增｜既有客戶成長

**要回答的問題**

> 哪些穩定客戶存在合理的補貨、品項擴張或服務深化機會？

**可能資料訊號**

- 歷史補貨週期接近，但近期尚未下單。
- 同類診所常見品項組合與該客戶現況存在缺口。
- 已採購品項與其他產品的適配關係。
- 過去活動、產品諮詢或試用回應。
- 客戶等級、歷史毛利及服務成本。

**任務卡輸出**

- 補貨提醒或品項機會假設。
- 同類客戶基準的正確定義與樣本數。
- 建議準備的產品資訊。
- 合規與通路適用條件提醒。
- 明確標示這是商業機會假設，最後仍由業務及產品規範把關。

## 五、統一任務排序引擎

### 5.1 為何不能沿用單一成交機率

單一成交機率容易優先挑出「即使不拜訪也可能下單」的客戶，無法回答外勤資源是否真正改變結果。三類任務的目標不同，也不能使用同一組欄位直接比較。

新版採兩層設計：

1. 各任務模型先產生該任務內部的需求、潛力或風險分數。
2. 統一任務價值層再考量商業價值、急迫性、可信度、拜訪成本及業務限制。

### 5.2 MVP 任務價值公式

四天版不把三種原始分數直接相乘。每類任務先在自己的候選群體內，將「任務訊號」與「相對商業價值」各自轉成 0–100 百分位，再使用同一組可解釋欄位形成任務價值分數：

```text
任務價值分數（0–100）
= 30% 任務訊號
+ 25% 相對商業價值
+ 20% 急迫性
+ 15% 證據強度
+ 10% 策略適配度
− 執行成本懲罰（0–20 分）
```

| 欄位 | 四天版定義 |
|---|---|
| 任務訊號 | 攻為新客適配、守為風險待查、增為補貨／品項機會；只在同類候選任務內轉成百分位 |
| 相對商業價值 | 在同類任務內依歷史營收、機會級距或客戶等級轉為百分位，不宣稱精確金額 |
| 急迫性 | 依逾期承諾、補貨時間窗、連續下降或接觸階段，使用 0／50／100 三段規則 |
| 證據強度 | 依資料完整度、訊號數量與最近更新時間分成弱／中／強，再映射為 40／70／100 |
| 策略適配度 | 依區域、科別、產品線與本期業務策略使用 0／50／100 規則 |
| 執行成本 | 電話 2 分；實訪預估交通 ≤30 分鐘扣 6 分、31–60 分鐘扣 10 分、>60 分鐘扣 15 分；缺少距離資料扣 12 分；特殊準備可再扣 0–5 分，合計上限 20 分 |

最終分數以 `max(0, min(100, score))` 截斷在 0–100。固定預約先占用可用時間；接著各類先取情境設定的最低配額，再以總分補滿剩餘時間。若某類沒有合格任務，該配額釋出給其他類型。配額必須標示為 Demo 情境設定，不宣稱為中化現行政策。

注意：此分數是排序工具，不應命名為「拜訪造成的增量營收」。正式試點累積 treatment／control 與任務結果後，才逐步估計真正的 incremental effect。

### 5.3 任務約束

排序不只看分數，還要處理：

- 業務負責區域與客戶權限。
- 診所可拜訪時段與預約狀態。
- 每日可用外勤／聯絡時間，而不是模糊的「任務數容量」。電話、實訪與固定預約使用不同預估工時。
- 必須完成的固定任務。
- 路程與交通限制。
- 近期已拜訪或已聯絡的排除條件。
- 產品與通路的適用限制。

缺值處理規則：必要觸發欄位缺失時不產生該類任務；非必要欄位缺失時不直接扣低商業價值，而是降低「證據強度」。同分時依序以急迫性、固定期限、證據強度及較低執行成本排序。

### 5.4 路線功能的位置

正確流程應為：

> 先決定哪些任務值得做，再針對已選任務安排合理路線。

地圖不是選客模型，也不能把直線連點稱為路線最佳化。四天版以固定預約優先，再用最近鄰啟發式排列其餘點位；介面名稱必須是「拜訪點位與建議順序示意」，並明示不是即時導航或最佳路線。

## 六、產品體驗與畫面架構

### 6.1 首頁：今日任務

首頁取消公司客戶總數、平均成交機率等大型 KPI，直接呈現：

- 今日待辦任務總數。
- 攻／守／增三類任務分布。
- 今日最高優先任務。
- 需要人工確認的弱證據任務。
- 尚未完成的固定追蹤事項。

每張任務卡至少包含：

```text
任務類型：守｜流失挽回
對象：安康診所
為什麼現在：主要品項連續兩期下降、45 天未有效互動
可能影響：近 6 個月平均月營收／核心品項關係
建議目的：確認庫存、需求變化與未完成承諾
準備資料：訂單趨勢、前次拜訪摘要、帳款狀態
證據強度：中；競品原因需業務確認
操作：採納／修改／延後／拒絕
```

### 6.2 任務審核頁

業務可對 AI 任務進行：

- 採納：加入今日行程。
- 修改：調整目的、時間或建議行動。
- 改為電話：不一定每個高分任務都需要實地拜訪。
- 延後：選擇原因與預計日期。
- 拒絕：記錄客情、資料錯誤或其他原因。

這些操作不是裝飾，而是後續模型改善與企業治理所需的標籤。

### 6.3 診所 360 任務頁

此頁只呈現完成任務需要的資訊：

- 任務目的與觸發證據。
- 訂單、品項與互動時間線。
- 前次拜訪摘要與未完成承諾。
- 帳款、售後或服務事項。
- 適合準備的產品資訊。
- AI 不確定之處。
- 任務完成後的結果回報。

### 6.4 行程頁

- 已確認任務的地理點位。
- 建議執行順序。
- 可拖曳調整。
- 顯示固定預約與彈性任務。
- 明確區分「商業優先順序」與「交通順序」。

### 6.5 主管頁（Roadmap，不列入四天 P0）

主管頁不做業務排名與紅黃綠數量競賽，未來版本改看：

- 高價值待處理任務是否被覆蓋。
- 任務採納、修改、延後與拒絕原因。
- 各任務類型的完成率與結果。
- 資料品質或系統性異常。
- 需要主管協調的跨區、產品或資源問題。

## 七、資料模型全面重做

### 7.1 核心資料表

| 資料表 | 主要內容 |
|---|---|
| `accounts` | 診所帳戶、區域、科別、規模、合作狀態、負責業務、座標 |
| `prospects` | 尚未合作診所、來源、適配特徵、接觸階段 |
| `interactions` | 拜訪、電話、活動、承諾事項、結構化結果與摘要 |
| `orders` | 日期、品項、數量、金額、毛利、退貨或取消 |
| `products` | 產品線、通路適用性、組合關係及必要限制 |
| `receivables` | 帳款狀態、到期日與異常；僅在業務權限允許時使用 |
| `reps` | 業務、區域、負責帳戶與每日可用分鐘數 |
| `tasks` | 任務類型、觸發原因、分數、狀態、建議與版本 |
| `task_reviews` | 採納、修改、延後、拒絕及原因 |
| `task_outcomes` | 是否執行、結果類型、後續訂單／互動、完成時間 |

四天 P0 不必完整建成十張正式資料表，只需下列最小欄位：

| P0 檔案 | 必要欄位 |
|---|---|
| `accounts` | account_id、name、specialty、region、status、rep_id、lat、lon、value_band |
| `prospects` | prospect_id、name、specialty、region、contact_stage、fit_band、lat、lon |
| `interactions` | account_id、date、channel、summary_tag、next_step、due_date、competitor_mentioned |
| `orders` | account_id、date、product_line、amount、quantity |
| `tasks` | task_id、target_id、task_type、reason_codes、signal_score、business_value_score、urgency_score、evidence_score、strategy_fit_score、cost_penalty、value_score、estimated_minutes、action_mode、is_fixed、appointment_time、status |
| `task_feedback` | task_id、decision、modified_action、reason、outcome、next_date |

`products`、`receivables` 與完整主管資料在 P1 再加入。P0 若沒有最小帳款資料，就不在 Demo 放入收款情境。

### 7.2 合成資料生成原則

新版資料必須模擬「事件與結果」，不能先設定答案再把答案直接餵給模型。四天 P0 的合成資料只用來驗證任務流程與介面，不使用由生成規則產生的 label 宣稱模型 Precision、AUC 或商業效果。

必須移除：

- `competitor_pressure` 這類不可在真實系統中直接觀察的隱藏真值欄位。
- 固定把 15% 客戶標為高風險的做法。
- 先依模型分數排序，再用同一模型分數宣稱效益提升的循環驗證。

新版合成資料應包含：

- 正常補貨、季節性與隨機波動。
- 真實可觀察的風險訊號，例如品項停購、互動中斷、客訴未結、明確競品文字標記。
- 新診所從未接觸、已接觸、約訪、試用、合作等階段。
- 任務是否被執行及執行後的觀察結果；明確區分「後續發生」與「由任務造成」。
- 不同通路或科別的不同基準線。
- 缺失值、延遲登錄與錯誤紀錄，以展示資料品質處理。

### 7.3 時間切分

正式模型訓練與驗證必須依時間切分；四天 P0 先保存正確時間欄位與資料邊界，不勉強產生無意義的模型指標：

- 以較早期間訓練。
- 以較晚期間測試。
- 避免同一客戶的相鄰快照同時出現在訓練與測試 folds，造成資訊洩漏。
- 所有特徵只能使用任務產生當下已知的資料。

## 八、AI 與規則模組

四天 P0 採「規則＋分析模型」混合式引擎，不包裝成三個已訓練完成的 AI 模型。AI 的價值在於跨來源整理訊號、產生候選任務、提供可讀理由、記錄人工回饋並於下一次批次重新計算；正式模型化放入企業試點 Roadmap。

### 8.1 攻：新客潛力引擎

第一版可採可解釋的分群或相似度模型：

- 找出與既有高價值診所相似的潛在診所。
- 依科別、區域、產品適配與接觸階段評分。
- 加入路線順訪成本，但不讓距離掩蓋商業價值。

若沒有可靠的未合作診所資料，Demo 應標示為「潛在客戶資料樣例」，不可宣稱已涵蓋真實全台診所。

### 8.2 守：流失待查引擎

第一版採「明確觸發規則＋異常偵測」雙軌：

- 明確觸發規則用來說明已知風險，例如核心品項停購、承諾逾期。
- 異常模型只負責發現不尋常變化，輸出名稱為「異常待查」。
- 只有出現直接競品訊號時，才標示「疑似競品因素」。

正式取得結果標籤後，再改成監督式流失風險模型。

### 8.3 增：補貨與品項機會引擎

- 補貨以個別診所歷史週期為優先，不只看全體平均。
- 品項機會比較同科別、同規模或相近需求的診所。
- 「同儕採購占比」必須明確區分訂單事件占比、客戶採用率與營收占比。
- P0 不輸出「應推薦哪個產品」的自動結論，只顯示補貨或品項機會證據及需要準備的產品資訊。正式門檻、同儕樣本量與法遵審核責任由產品負責人確認後才啟用。

### 8.4 解釋層

每個任務必須輸出：

- 觸發任務的三項主要證據。
- 與個別診所歷史或合理同儕的比較。
- 證據強度與資料完整度。弱／中／強只描述任務證據，不假裝是跨模型校準後的機率。
- 不確定或需要人工確認的原因。
- 模型版本與任務生成時間。

不得把全域 feature importance 加上百分位，直接稱為單一客戶的模型因果解釋。

## 九、Demo 故事板

### 9.1 開場情境

時間：週一上午，診所通路業務準備外出。

介面先讀取固定預約，再由業務輸入今日可用的聯絡／外勤時間。電話與實訪使用不同預估工時。Demo 不說「每位中化業務固定拜訪五家」，而說「本次展示情境有兩個固定預約與四小時彈性任務時間」。

### 9.2 今日任務清單

展示五張不同任務卡：

1. 守：核心品項停購且未完成回訪的既有診所。
2. 攻：位於服務區、與產品線高度適配的新診所。
3. 增：接近個別補貨週期的穩定診所。
4. 守：售後問題未完成，先電話確認。
5. 增：存在品項組合缺口，但證據強度偏低，需業務確認。

### 9.3 深入一張「守」任務

- 顯示訂單與品項時間線。
- 顯示前次拜訪摘要及逾期承諾。
- 系統說明「流失風險待查」，不直接宣稱競品入侵。
- 業務補充現場資訊，修改任務目的並採納。

### 9.4 深入一張「攻」任務

- 顯示新診所為何與產品線適配。
- 顯示其鄰近已確認任務，不以距離作為唯一理由。
- 業務將首次接觸改為電話約訪，避免無預約直接拜訪。

### 9.5 形成行程

系統只針對已採納且需實地拜訪的任務安排點位順序。電話任務不進入路線。業務可拖曳調整，AI 保留修改原因。

### 9.6 回饋閉環

任務完成後，業務選擇結果：

- 完成／未完成。
- 需求確認／補貨／後續約訪／無機會／資料錯誤。
- 下一步日期與承諾事項。

系統立即寫回任務狀態，並在下一次批次計算時更新候選任務；不因單筆回饋即時重訓模型。模型更新必須累積足夠資料、離線驗證並經版本審核。系統不把「按下採納」或任務後出現訂單直接當成增量效益。

### 9.7 三分鐘 Demo 節奏

| 時間 | 展示內容 |
|---|---|
| 0:00–0:20 | 情境、固定預約與四小時彈性時間 |
| 0:20–0:45 | 今日攻／守／增任務清單 |
| 0:45–1:30 | 深入「守」任務並由業務修改後採納 |
| 1:30–1:55 | 「攻」任務改為電話約訪 |
| 1:55–2:15 | 快速展示「增」任務與低證據情境 |
| 2:15–2:35 | 只對實訪任務形成點位順序 |
| 2:35–3:00 | 結果回饋、驗證邊界與結尾 |

## 十、驗證與效益設計

### 10.1 合成資料階段可以證明什麼

- 三類任務能由資料生成。
- 任務有一致的證據、狀態與人工回饋流程。
- 不同任務可在同一介面比較與安排。
- 系統可處理資料缺失與弱證據情境。

### 10.2 合成資料階段不能證明什麼

- 真實成交率提升。
- 真實客戶流失降低。
- 競品入侵被成功攔截。
- 人均產值實際增加。

### 10.3 離線模型指標（企業試點後）

取得真實結果標籤後，再依任務選擇適合指標；四天版不以合成 label 計算下列數字作為成效：

- 攻：Precision@K、Recall@K、校準度及實際開發階段轉換。
- 守：Precision@K、PR-AUC、提前預警天數及誤報率。
- 增：補貨預測誤差、品項機會命中率及校準度。
- 排序：Top-K 任務覆蓋的已知機會／風險比例。

AUC 可以保留在技術附錄，但不能代替營運價值。

### 10.4 真實試點 KPI

| 層級 | KPI |
|---|---|
| 採用 | 任務查看率、採納率、修改率、拒絕原因、回饋完整率 |
| 效率 | 有明確目的的拜訪比例、每項任務準備時間、無效拜訪率 |
| 攻 | 新診所有效接觸率、約訪率、階段轉換率 |
| 守 | 風險確認率、挽回率、核心品項恢復率、預警提前時間 |
| 增 | 補貨命中率、品項擴張率、增量毛利 |
| 治理 | 弱證據任務比例、資料錯誤率、人工覆核率、權限事件 |

### 10.5 試點方法

- 先由小範圍診所通路團隊使用。
- 依區域、客戶價值與歷史績效做平衡分組。
- 比較 AI 任務組與既有規劃方式。
- 主要結果使用真實任務完成與後續營運資料。
- 逐步累積「做／不做某任務」的結果，未來才有條件估計 uplift。

## 十一、資訊治理與落地邊界

- 只顯示業務有權查看的責任區域與客戶資料。
- 客戶層級以醫療機構及專業通路為主，不使用病患個資。
- AI 任務必須可覆核、可拒絕、可追溯。
- 任務需保存模型版本、資料時間與人工修改紀錄。
- 產品建議必須遵守內部產品資訊與通路適用規範。
- 競品、客訴、帳款等敏感原因不可僅由模型臆測。
- 正式串接 SAP、CRM、OA 前，先以最小欄位 CSV／API 試點。

## 十七、簡報用語護欄

### 可以說

- 「以合成資料驗證任務生成與人機協作流程。」
